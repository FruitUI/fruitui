# Component policy

FruitUI components are organized by semantic purpose. Configuration changes the presentation of that purpose. Independent behaviors are composed from independent controls.

This policy is the acceptance rule for new components and API changes. The Blade validators reject unsupported options and semantic overrides. The contract tests require a catalog entry for every Blade component and exercise native controls and adapter behavior. Review still establishes whether a proposed abstraction has a distinct purpose and evidence of reuse; an automated test cannot determine that design judgment.

## Choosing the smallest appropriate change

| Need | Approach |
| --- | --- |
| Different color, spacing, or radius | Override an existing `--f-` design token in the relevant scope. |
| Primary, danger, or quiet button styling | Use an explicit variant of Button. |
| Different text, icon, description, or trailing content | Use a slot or compose existing layout classes and primitives. |
| A layout row containing a checkbox | Place Checkbox in the row; Checkbox owns checked state and the submitted value. |
| A distinct accessible purpose, value model, or interaction | Give that semantic control its own primitive and contract. |
| A recurring arrangement of primitives | Extract a pattern after two actual application/example uses demonstrate the need. |

Each public component must have a one-sentence purpose and document its native element/role, value or state, keyboard behavior, options, and slots. Prefer a small set of named options to unrelated boolean mode flags. Do not introduce `checkboxMode` on a list, a generic `as` prop on controls, or a component per button color. Shared CSS can serve separate semantic components.

Native HTML subtypes within a documented family are allowed: email and password are text-entry fields, button can submit a form, and a native select can have `multiple`. These retain the declared control purpose and use browser behavior. Selection controls, file pickers, date pickers, numeric spinners, and sliders are not text-like Input subtypes in FruitUI. They have dedicated adapters, share control-frame CSS where appropriate, and retain distinct native value and keyboard contracts.

## Required light and dark appearances

Every component, composed pattern, and example must work in both light and dark appearances. This includes default, hover, focus, checked/selected, invalid, and disabled states, plus menus, dialogs, backdrops, and other overlays. Text, icons, control boundaries, and state indicators must remain readable in each appearance.

CSS follows `prefers-color-scheme` by default on each `.fruit-ui` scope and updates when the system preference changes. An omitted `data-theme` or `data-theme="system"` enables this behavior. No Alpine initialization, Livewire request, JavaScript media listener, or reload may be required. Optional `data-theme="light"` and `data-theme="dark"` overrides remain available on the same scope. Set `color-scheme` alongside the palette so native controls use the matching appearance.

Use shared semantic `--f-` tokens for colors, shadows, and backdrops. Define every new color/effect token in both palettes; automatic and explicitly selected dark appearances must use the same values. A value may deliberately stay the same in both palettes when it remains suitable, such as white content on a filled accent control. Core component CSS must not contain fixed color literals. Theme-independent decorative artwork, such as the example logo and window dots, can retain its identity colors after review in both appearances; text and control states still follow semantic tokens.

Custom token overrides must supply suitable light and dark values and preserve automatic switching and explicit overrides. Do not force an example or component to light mode. Browser checks enforce paired tokens, prevent fixed colors in core component styles, and verify automatic switching and explicit overrides without JavaScript. Existing gallery/Mail accessibility checks cover both appearances; review new visual states as part of change acceptance.

Native attributes and `x-*`/`wire:*` bindings belong on the underlying element, not the surrounding label. Checkbox, Radio, and Switch share `f-check`/`f-switch` styling rather than adding per-state components. Both checkbox and radio examples already exist in the component gallery; the Blade wrappers expose those native contracts to Laravel.

Fieldset is a native grouping primitive, reused by Admin notification settings and the Support reply/note group. It never owns its child values. Checkbox and Radio share `f-check`, including direct `input.f-check` for table selection; `--f-check-size` adjusts size without changing behavior. Checked, indeterminate, invalid, disabled, focus, and forced-colors rendering belong to shared CSS. Native blockquote/code/kbd/hr/pre receive baseline typography within `.fruit-ui`; they need no per-tag Blade components or behavior modes.

The CSS-only `.f-avatar` presents initials as an identity cue. Use a native span with no interaction or selection state; mark it `aria-hidden="true"` when an adjacent name supplies the identity, or provide an accessible name when it stands alone. It has no behavior options, added keyboard behavior, or value model. Scoped size, radius, border, surface, color, and typography tokens support square workspace initials without another component. Mail sender/account identities and Support customer/agent identities are its two actual uses, so its unchanged styling belongs in shared `components.css`.

The `.f-sidebar__group` navigation pattern composes a native `details`/`summary` disclosure with independent links or buttons using `.f-sidebar__item--nested`. Its two actual uses are Mail account folders and Support team mailbox views. The disclosure owns only its native `open` state and Enter/Space interaction; child controls own navigation actions and `aria-current`. `.f-sidebar__identity` arranges optional primary/secondary text; `.f-sidebar__chevron` is a decorative icon that follows native open state. There are no behavior modes or new Blade primitives. Counts, account/mailbox ownership, the virtual `all` scope, and folder filters belong to application data in `examples/`, not this CSS pattern.

## Runtime boundaries

- Input rejects types outside its text-like allowlist, including checkbox/radio, number, date, range, file, and hidden.
- Button rejects unknown variants and types. Unknown values raise clear exceptions rather than falling back to default styling.
- Controls keep their element and role. `as`, incompatible `type`/`role`, and explicit client `:type`/`x-bind:type`/`:role`/`x-bind:role` bindings are rejected. Server-bound Blade `:type` and `:variant` props are validated at render time.
- Matching fixed choice type/role attributes are accepted and emitted once. Input and Select infer their roles from native HTML and reject explicit role overrides; the other controls accept only their declared role. Card permits group/region roles and rejects interactive roles such as checkbox or button.
- Normal labels, native form attributes, custom classes, `aria-*` descriptions/validation, and Alpine/Livewire value and action bindings continue to pass through.

Plain HTML/CSS consumers follow the same documented contracts through their markup. Runtime validation belongs to the Blade adapters; arbitrary consumer JavaScript or attribute spread objects are outside that validation boundary. Keep that distinction explicit in claims about enforcement.

## Pattern and adapter rules

Use `f-row`, `f-stack`, and slots to compose content before adding API options. A row with a checkbox is ordinary composition:

```blade
<div class="f-row">
    <x-fruit::checkbox name="selected[]" value="message-42" wire:model="selected">
        A fresh start for FruitUI
    </x-fruit::checkbox>
    <span class="f-badge">Unread</span>
</div>
```

The layout owns arrangement; the checkbox owns selection. Conversation rows now have two actual uses in Mail and Support. The shared `.f-conversation-list` is a native list, and `.f-conversation-row` is the button that opens an item. Put a bulk-selection checkbox beside the button inside a list item, never inside the button. Slots within the button contain only noninteractive content; the row does not own checked state or switch to checkbox/listbox semantics. Quiet and filled change only presentation. Padding, radius, separator insets, and current-state colors use scoped `--f-conversation-*` tokens; each example retains its own responsive geometry and navigation callbacks.

The `.f-attachment` native link is shared by Mail and Chat; `.f-empty-state` is shared by Mail, Support, Chat, and Admin. Their CSS and Blade wrappers use the same arrangement and attribute ownership. File URLs, downloads, filters, and recovery actions remain application concerns. Attachment spacing uses `--f-attachment-gap` and `--f-attachment-padding`; empty-state spacing and typography use `--f-empty-gap`, `--f-empty-padding`, `--f-empty-min-height`, `--f-empty-title-size`, and `--f-empty-description-size`. Any custom appearance overrides still require light/dark values.

Mail, Support, Chat, and Admin are the current reference interfaces. Their sample data and application behavior stay in `examples/`; Support's ticket layout, conversation threads, and customer inspector are example compositions. Chat reuses Toolbar, Sidebar groups, Avatar, native form controls, and Dialog; its message flow and full thread arrangement stay in `examples/chat/`; floating disclosures and composers reuse the shared patterns. A reaction is an independent native button with `aria-pressed`; a message row does not become a selection control. Channels, unread state, and drafts are application state rather than control options. Admin composes native tables, independent selection checkboxes, sort/action buttons, forms, and SVG charts in `examples/admin/`. Its sidebar reuses the existing disclosure pattern. Its customer tabs, breadcrumbs, and hash routing remain example-local: tab buttons have fixed tab roles, linked panels, selection state, and Left/Right/Home/End behavior; navigation links retain native link semantics. Records and record tabs do not become sidebar behavior modes. Shared native Table presentation is now a distinct primitive used by the customer and subscription tables. It does not own CRUD behavior; records, pagination, and chart series belong to the application. Additional interfaces should demonstrate actual shared needs before producing more reusable patterns. Core primitives can start from one real use when they represent a distinct native control.

CSS handles appearance and layout, Blade emits the same native controls, Alpine adds local state, and Livewire adds server actions. Their semantic contracts remain the same. Do not add a second Alpine instance, automatic DOM role switching, or adapter-specific behavior flags. Test a control's changed behavior and integration; use the existing gallery checks for light/dark, focus, accessibility, and narrow layouts.

Server-driven examples use Livewire 4 single-file components, keeping PHP state/actions and Blade markup together in the class-based format previously provided by Volt. Reusable native controls remain thin Blade adapters and work without Livewire. Laravel adapters target Laravel 13 and PHP 8.3+.

## Change acceptance

Before adding a primitive or option, describe the requested use, the semantic purpose, existing composition considered, supported options, and attribute ownership. For a new pattern, name its two actual uses. Update the contract catalog and relevant gallery examples, retain adapter parity, verify every affected state in light and dark appearances, and add focused regression coverage for new behavior or validation. `composer test`, `npm run build`, and `npm test` must pass for component changes.

The machine-readable [component catalog](component-catalog.json) lists every public CSS family, its gallery anchor, any Blade adapters, and actual uses for extracted patterns. Browser checks compare all core `.f-*` selector families (including new CSS files) against this catalog, require a live gallery specimen plus HTML and Blade usage for every entry, and check that each extracted pattern appears in at least two named examples. PHP checks separately require a documented contract for every Blade wrapper. These checks catch missing inventory, adapters, examples, and documentation; they do not decide whether two arrangements deserve one semantic abstraction. Review must still compare repeated arrangements when adding an example, extract their common presentation, and explain any differences that remain local. Do not postpone extraction by labeling an already repeated pattern example-specific. The original Mail shell is cataloged as the initial reference pattern; Charts/breadcrumbs, full Support inspectors, and Chat message arrangements remain example-local. Tabs, pagination, section navigation, and rich message content now have shared contracts and presentation. Workspace/panes are reused by all four examples; Composer by Support/Chat; Description List by Support/Admin; Floating Disclosure by Mail/Chat. The splitter is a distinct optional resizing control, used on the same frames. Table exposes native tabular presentation, used by two Admin tables.

## Shared workspace and presentation boundaries

Workspace and Pane own frame chrome, surfaces, borders, and scroll/focus treatment. Applications define column placement, width tokens, container queries, and which panes are visible. Splitter changes one declared width token within bounds, preserving the flexible content pane's reserved width. Hide handles whenever panes are stacked, hidden, or replaced by compact navigation; retain the same CSS layout without Alpine. Widths stay local to the mounted workspace and are not persisted automatically.

Composer never owns draft values, textarea labels, delivery mode, or sending shortcuts. Description List never owns record data. Floating Disclosure remains native details/summary; independent child buttons do not acquire menu roles. Table retains caption/headers and separate checkboxes/actions; selection presentation uses data-selected, not a grid role. These boundaries apply equally to HTML, Blade, Alpine and Livewire.

Design references: [Apple layout](https://developer.apple.com/design/human-interface-guidelines/layout) and [column views](https://developer.apple.com/design/human-interface-guidelines/column-views) support adapting layouts and resizing columns. [WAI window splitters](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/) describes named separators, pane relationships, values, and directional keys. FruitUI's bounded splitter keeps panes open; collapse/navigation belongs to the application.


## Support interface additions

Menu is a command primitive, distinct from Floating Disclosure's independent ordinary controls. Combobox chooses one existing option; Token Field edits a list serialized as a newline string; Editor stores HTML. Their different values and keyboard contracts justify distinct primitives. Select and Textarea keep their original contracts.

Input Group, Button Group, Chip, Upload rows, grouped notifications, avatar groups and presence compose independent controls. They never own delivery, upload transport, validation rules, read state or routing. Shared Input Group is used for Support tags and Admin trial units. Prose is reused by Mail and Support message bodies; Presence by Support and Chat. Upload presentation is used in Mail compose and Support new conversations; the local simulation lives only in examples/shared/uploads.js. Admin's route-aware tabs retain its existing navigation callbacks while sharing f-tabs/f-tab presentation.

Enhanced form controls keep one canonical named native control. Helpers forward native input events and committed change events, external Alpine model updates, resets, labels and native invalid focus to the visible UI. Applications must validate recipient strings and sanitize rich HTML on the server. Register fruitui/editor separately if you want Tiptap; core fruitui/alpine does not import an editor. Without scripts, single choices are selects and token/HTML documents are textareas. Tooltip content is supplementary, noninteractive text referenced by aria-describedby; its helper adds Escape dismissal.

## Adoption contracts

Enhanced controls accept a `wrapper` attribute array (id/class/style/dir/lang/data-*); form identity, bindings and actions stay on the canonical control. Its class/style presentation is mirrored to the visible control. Wrappers may not own x-data or wire:model. Attribute, value, option and reset changes synchronize separately; option changes preserve pending searches. All ancestor fieldsets participate in disabled state. Token Field maxlength limits the full newline-serialized value; it does not limit each token's query.

Combobox and Token Field commit discrete values with input/change. Editor emits input while typing and change when focus leaves the whole widget, including its toolbar. Focus/blur bindings stay on the native control. Toolbar is an optional Editor named slot containing independent native command buttons; commands remain the documented seven, and application-supplied labels are ordinary content. Default Blade labels use Laravel translations.

Nested tabs and menus own only their descendants with the matching nearest helper root. Tabs follow inline direction for arrows. Shared popup positioning serves Combobox, Menu, Tooltip and Floating Disclosure while preserving their distinct roles. Toast timing is composed through fruitToast in Mail, Support, Chat and Admin; replacing a message cancels its predecessor, pause/resume allows reading, and destruction clears timers.
