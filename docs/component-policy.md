# Component policy

FruitUI components are organized by semantic purpose. Configuration changes the presentation of that purpose; independent behaviors come from composing independent controls. This policy is the acceptance rule for new components and API changes.

What is enforced automatically:

- Blade adapters reject unsupported options, element/type/role overrides and client bindings that would change a control's kind ([ComponentContract](../src/Laravel/Support/ComponentContract.php)).
- Every Blade adapter needs a contract in [component-catalog.json](component-catalog.json); the table below is generated from it (`npm run build:docs`).
- Every public CSS family needs a catalog entry, a live gallery specimen, and HTML and Blade usage. Extracted patterns need two actual example consumers.
- Light and dark palettes stay paired; core CSS contains no fixed colors.

Review still decides whether a proposed abstraction has a distinct purpose and evidence of reuse.

## Choosing the smallest appropriate change

| Need | Approach |
| --- | --- |
| Different color, spacing, or radius | Override an existing `--f-` design token in the relevant scope. |
| Primary, danger, or quiet button styling | Use an explicit variant of Button. |
| Different text, icon, description, or trailing content | Use a slot or compose existing layout classes and primitives. |
| A layout row containing a checkbox | Place Checkbox in the row; Checkbox owns checked state and the submitted value. |
| A distinct accessible purpose, value model, or interaction | Give that semantic control its own primitive and contract. |
| A recurring arrangement of primitives | Extract a pattern after two actual application/example uses demonstrate the need. |

Each public component has a one-sentence purpose and documents its native element/role, value or state, keyboard behavior, options, and slots. Prefer a small set of named options to unrelated boolean mode flags. Do not introduce `checkboxMode` on a list, a generic `as` prop on controls, or a component per button color. Shared CSS can serve separate semantic components.

Native HTML subtypes within a documented family are allowed: email and password are text-entry fields, a button can submit a form, and a native select can have `multiple`. Selection controls, file pickers, date pickers, numeric spinners, and sliders are not text-like Input subtypes. They have dedicated adapters, share control-frame CSS where appropriate, and keep distinct native value and keyboard contracts.

## Light and dark appearances

Every component, pattern, and example works in both light and dark appearances, including hover, focus, checked/selected, invalid, and disabled states, plus menus, dialogs, backdrops, and other overlays. Text, icons, control boundaries, and state indicators remain readable in each appearance.

CSS follows `prefers-color-scheme` on each `.fruit-ui` scope and updates live when the system preference changes. An omitted `data-theme` or `data-theme="system"` enables this; no Alpine, Livewire request, media listener, or reload is involved. `data-theme="light"` and `data-theme="dark"` override it on the same scope. Set `color-scheme` alongside the palette so native controls match.

Use shared semantic `--f-` tokens for colors, shadows, and backdrops, and define every new color/effect token in both palettes. A value may stay the same in both palettes when it suits both, such as white content on a filled accent control. Core component CSS contains no fixed color literals. Theme-independent artwork, such as the example logo, may keep its identity colors after review in both appearances.

Custom token overrides supply suitable light and dark values and preserve automatic switching and explicit overrides. Do not force an example or component to light mode.

## Runtime boundaries

- Input rejects types outside its text-like allowlist, including checkbox/radio, number, date, range, file, and hidden.
- Unknown option values raise clear exceptions rather than falling back to default styling.
- Controls keep their element and role. `as`, incompatible `type`/`role`, and client `:type`/`x-bind:type`/`:role`/`x-bind:role` bindings are rejected. Server-bound `:type` and `:variant` props are validated at render time.
- Matching fixed type/role attributes are accepted and emitted once. Input and Select infer their roles from native HTML; containers accept only their documented grouping roles.
- Helper-owned attributes (`x-data` on Menu, Tooltip and Toaster; enhancement visibility on Combobox, Token Field and Editor; orientation and focus on Splitter) cannot be overridden or bound.
- Labels, native form attributes, custom classes, `aria-*` descriptions/validation, and Alpine/Livewire value and action bindings pass through to the real control.

Plain HTML/CSS consumers follow the same documented contracts through their markup. Runtime validation belongs to the Blade adapters; arbitrary consumer JavaScript and attribute spreads are outside it.

## Composition and adapter rules

Use `f-row`, `f-stack`, and slots to compose content before adding API options. A row with a checkbox is ordinary composition; the layout owns arrangement and the checkbox owns selection:

```blade
<div class="f-row">
    <x-fruit::checkbox name="selected[]" value="message-42" wire:model="selected">
        A fresh start for FruitUI
    </x-fruit::checkbox>
    <span class="f-badge">Unread</span>
</div>
```

CSS handles appearance and layout, Blade emits the same native controls, Alpine adds local state, and Livewire adds server actions. Their semantic contracts are identical. Do not add a second Alpine instance, automatic DOM role switching, or adapter-specific behavior flags.

Native attributes and `x-*`/`wire:*` bindings belong on the underlying element, not a surrounding label or wrapper. Enhanced controls (Combobox, Token Field, Editor) keep one canonical named native control that owns names, models and validation; generated UI lives in `wire:ignore` containers beside it. Without scripts, single choices are selects and token/HTML documents are textareas.

Server-rendered markup must survive Livewire morphs: anything a helper adds at runtime is either in a `wire:ignore` container or reapplied by the helper. Accessibility associations (IDs, `aria-describedby`) are rendered by the server rather than added by scripts. Server-driven examples use Livewire 4 single-file components.

## Ownership boundaries

These apply equally to HTML, Blade, Alpine and Livewire. Actual uses of each pattern are listed in the catalog.

- **Item List / Item Row:** the list is a native list, not a listbox; the row is a button that opens one item. Quiet and filled change only presentation. Put a bulk-selection checkbox beside the button inside the list item, never inside it. Slots inside the button hold noninteractive content only. Applications own which item is open (`aria-current`), arrow-key navigation and responsive geometry.
- **Workspace / Pane / Splitter:** Workspace and Pane own frame chrome, surfaces, borders and scroll/focus treatment. Applications define columns, width tokens, container queries and pane visibility. Splitter changes one declared width token within bounds while reserving the flexible pane's width; it never collapses panes or persists widths. Hide handles whenever panes stack or are replaced by compact navigation.
- **Composer** never owns drafts, textarea labels, delivery mode or sending shortcuts. **Description List** never owns record data. **Table** keeps caption/headers and separate checkboxes/actions; selection presentation uses `data-selected`, not a grid role, and sorting uses caller-owned `aria-sort`.
- **Menu** is a command primitive. **Floating Disclosure** stays native details/summary; its independent controls do not acquire menu roles, and there is no focus trap.
- **Avatar** is an identity cue with no behavior. **Sidebar** composes native links and details/summary groups; counts, ownership and filters belong to the application.
- **Toast** is a status container whose text the application owns. **Toaster** owns one message and its timing and listens for `fruit-toast` events; it does not route or queue notifications. Use Alert or Dialog for messages that need a response.
- **Field** associates one control with its label, description and error, including the shared validation error for the control's `wire:model` or `name`. It owns no value, rule or model. Use Fieldset for independent choice groups.
- **Input Group, Button Group, Chip, Upload rows, Notifications, Avatar groups and Presence** compose independent controls and never own delivery, uploads, validation, read state or routing.
- Example-local arrangements (charts, breadcrumbs, full Support inspectors, Chat message threads, the Mail shell's data views) stay in `examples/` until a second actual use exists. The Mail shell is cataloged as the initial reference pattern and ships as the opt-in `fruitui/mail.css`.

## Change acceptance

Before adding a primitive or option, describe the requested use, the semantic purpose, the existing composition considered, supported options, and attribute ownership. For a new pattern, name its two actual uses. Then:

1. Add or update the catalog entry, including its contract, and run `npm run build:docs`.
2. Add the gallery specimen and HTML usage, then run `composer gallery`.
3. Keep adapter parity across HTML, Blade, Alpine and Livewire.
4. Verify every affected state in light and dark appearances.
5. Add focused regression coverage for new behavior or validation.

`composer test`, `composer lint`, `npm run lint`, `npm run build`, `npm test`, and `npm run test:package` must pass. When adding an example, compare repeated arrangements with existing examples and extract their common presentation once two real uses exist; explain any differences left local.
